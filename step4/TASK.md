# Step 4：把订单统计放到 Doris 的 FE/BE 架构里

- 发布日期：2026-09-23
- 预计用时：30–40 分钟，可随时完成并继续。
- 目标：建立查询全链路的第一张系统图，为下一步实际运行 Doris 做准备。
- 前置：你已经验证局部集合合并、分组键及 Bitmap 的基本行为。本步从数据结构回到整个系统，不继续深入位图实现。
- 形式：短文阅读 + 自己画图或写箭头链 + 环境现状记录。不要求编译或安装软件。

## 阅读入口与最小背景

阅读 [Doris 官方系统架构](https://doris.apache.org/zh-CN/docs/4.x/features-architecture/system-architecture/) 中“存算一体架构”的“核心组件”；再浏览“存算分离架构”的组件图即可，约 10 分钟。不用通读性能、高可用、索引等全部内容。

本步以存算一体、内部订单表为范围：FE 接入 SQL，负责解析规划、协调执行和元数据管理；BE 负责数据存储和执行查询计划。存算分离则引入共享存储及 Meta Service 等角色，后续单独展开。

注意：FE 的 Frontend 是数据库的前端节点，并不是浏览器里的网页前端。你的 Java 贡献入口主要在这里。

## 三个步骤

1. **把角色和数据流画出来，10–15 分钟。** 假设 orders 的不同数据分片放在两个 BE 上，查询仍然是按城市统计金额、订单数和去重用户数。画出客户端、一个 FE、两个 BE；标出 SQL、执行计划、扫描数据和中间结果分别出现在哪里。可以用纸笔图片、Mermaid 或纯文字箭头，重点是说明谁决定做什么、谁实际处理订单行。
2. **检查自己的系统模型，10–15 分钟。** 分别解释：为什么不是把所有订单行都拉到 FE 用 Java 聚合？Step 3 的 BitSet 类比的是规划工作还是执行时的状态？局部结果在节点间合并时为什么仍要带城市这个分组信息？不确定的部分明确标注，图是教学模型，不要求猜出真实优化器的完整执行计划。
3. **记录运行环境现状，5–10 分钟。** 写清本机 Doris 目前属于“仅有源码 / 已编译 / 已启动 / 已成功执行 SQL”哪一阶段。若已编译或运行，可提供非敏感的启动方式、版本和本地输出目录；若只有源码，直接说明。不要为完成这个记录临时跑全量编译，也不要贴密码。最后列出至多两个最想通过真实运行解答的问题。

## 防止形成错误模型

“结果最终返回客户端”和“所有原始订单都搬到 FE 计算”不同。图中的局部聚合、交换、最终聚合及排序具体如何分布，要以届时 Doris 的实际执行计划为准；不要固定认为最终聚合一定在 FE 或指定某个 BE 上。本步优先明确控制与执行职责。

## 验收标准

- 区分 FE 的接入、规划协调与 BE 的存储、执行职责。
- 图中区分查询计划、原始数据和中间结果，不把 FE 画成所有订单行的 Java 计算中心。
- 将 Step 3 的分组和聚合状态连接到查询执行，并保留同城合并的条件。
- 如实描述现有环境，方便后续安排一个能运行的最小 Doris 实验。未编译不算本步失败。
