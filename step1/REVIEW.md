## 一个直接补齐的知识点：多列排序

```sql
ORDER BY city_total_amount DESC, city ASC;
```

从左到右比较：先按金额降序；金额相同才按城市升序。不是先把全表按金额排完，再单独把全表按城市重新排序。

参考查询（教学反馈，不计作本人已独立完成的成果）：

```sql
SELECT
    city,
    SUM(amount) AS city_total_amount,
    COUNT(*) AS order_count,
    COUNT(DISTINCT user_id) AS paying_user_count
FROM orders
WHERE status = 'PAID'
  AND created_at >= '2026-08-23 00:00:00'
  AND created_at < '2026-09-22 00:00:00'
GROUP BY city
ORDER BY city_total_amount DESC, city ASC;
```

COUNT(*) 直接表达行数；你的 COUNT(order_id) 在 order_id 非空时同样正确，不需要为了风格认定原答案错误。字符串统一使用单引号，减少 SQL 方言或模式造成的歧义。

你写的“最高金额城市”使用 LIMIT 1，作为只取一个城市的需求是合理的；若并列时也要确定返回哪个城市，可增加 city ASC；若需求是“所有并列第一”，则 LIMIT 1 不满足。你没有要求全部并列，所以这一点不算错误。

依据：[Doris SELECT 官方文档：ORDER BY 与列别名](https://doris.apache.org/docs/4.x/sql-manual/sql-statements/data-query/SELECT/)。

## 三个需要校准的判断

1. **按 ID 查询不等于一次磁盘 IO。** 可能命中缓存，也可能需要多次页访问；是否走合适索引、是否需要额外读取数据、是否能定位分片，都会影响成本。当前更准确的说法是“具备合适索引和路由时，通常只需访问较少数据”。
2. **分表键必须与查询条件一起考虑。** 若按 user_id 分表，而查询只有 order_id，且没有额外路由信息，不能直接确定目标表。按日期分表也一样：查询不带日期时，需要另外解决定位问题。因此“做好分表就快”不能作为普遍结论。
3. **分布式执行不保证亿级数据秒级返回。** 你提到过滤下推、分布式执行与聚合，说明接触过相关概念，但这些尚未通过实验验证。还要看实际扫描量、去重用户数、数据分布、网络、硬件与并发等。SQL 写法也不等于物理执行顺序，后面用执行计划建立这层认识。
