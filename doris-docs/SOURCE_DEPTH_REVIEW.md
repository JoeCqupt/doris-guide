## 1. 结论与上轮判断修正

**需要继续补，而且核心工作是重写关键小节，不是继续增加概念专题。** 目前全书更适合定位为“Doris 架构与源码导航，附若干局部实现分析”。目录完整、技术名词出现、给出方法名，与读者能够独立理解实现之间还有明显距离。

上一轮九篇专题补足了主题覆盖和部分方法链，却没有逐一补足算法、对象变化、锁与失败处理。上一轮“缺口补齐”应理解为覆盖层面的增补，不能作为源码深度已完成的结论。这是编写质量需要调整，并非读者基础不足。

本轮遍历 28 章和 9 篇专题的结构与代码围栏，重点细读第 5、6、8、9、11、15、16、27 章及查询、优化、导入、内存、Cloud 专题；对规则与聚合的代表性原码做只读抽查。不是对所有技术断言逐条复证。本轮不执行 Git 命令，不运行服务或测试，不更新远端。

## 2. 为什么读起来像概念介绍

### 2.1 提供了入口，却把解释留给读者

例如第 6 章告诉读者去看 Memo.copyIn、StatsCalculator.estimate、CostCalculator.calculateCost，但没有拿一个计划展示 Group 如何创建、候选怎样入组、属性如何成为搜索条件、最优候选如何更新。读者知道“去哪里找”，仍不知道“它到底如何做”。

第 15 章知道 insert、flush、build_rowset、commit_txn 的职责，但未带着同一个 Block 走过行下标选择、MemTable 状态、Flush Token 和 Rowset 元信息变化。箭头连通并不等于数据过程已经讲明白。

### 2.2 分支边界提示多，命中条件和处理动作少

“有不同路径”“需要结合配置”“不能泛化”在范围声明处有用；每小节反复提醒，却不选择一条路径讲透，就把应由作者完成的分析转移给读者。应明确选定普通内表、具体 Key 模型、具体入口，再用代码证明该路径。

### 2.3 示例解释数学，尚未映射实现

AVG 的 sum/count 示例正确，IVM 的增量代数也有价值；但缺少聚合状态的分配/寻址、序列化缓冲和调用方如何选择 add/merge，或增量计划节点如何由代码构造。算法说明必须再落到变量与对象。

### 2.4 测试大多是目录，未成为论证

第 27 章会解释测试实际输入与断言，是值得保留的写法；其他很多章仅列测试文件，再建议将来验证。测试入口不是测试分析。没有运行环境仍可展开现有测试的夹具、调用和断言，运行状态单独标记。

### 2.5 主章与补充专题分散

一个读者要在第 6 章、专题 2、附录中拼接优化流程。部分主章仍写“尚未展开”，专题却已部分涉及，状态没有同步。这增加跳读成本，也让局部缺口难以辨认。

28 章和九篇专题中未检出 Java/C++ 语言标记的源码围栏（现有多为 SQL、流程图、文本箭头及命令）。这只是一个信号，不证明没有源码分析；但结合上述内容，可以确认短源码摘录和逐段解释明显不足。增加围栏数量本身也不是修复。

## 3. 按阅读目标评估

采用四层描述，不给虚假的完成百分比：

- L1：解释模块职责和系统位置。
- L2：解释具体方法、关键条件及部分数据变化。
- L3：以固定案例走通实现，含结构/状态演进、正确性和测试断言。
- L4：在 L3 上增加可复现的运行、失败或调试证据。

同一章可以部分达到 L2、其余仍为 L1。整体不因最深的小节而升级。

| 范围 | 当前判断 | 需要怎样处理 |
|---|---|---|
| 1—3 系统与读写全景 | 适合作为 L1 入门；历史 SQL/计划另有实证 | 保留导读，不必把所有基础概念写成逐行源码 |
| 4—5 请求、绑定、规则 | 局部 L2；规则例子较好 | 补对象输入输出、分支原码与规则测试，先做一章 L3 样章 |
| 6 优化搜索 | L1 为主，MV 有局部 L2 | 核心重写：一个 Join 的 Memo、属性、统计、代价与赢家选择 |
| 7 调度与 Exchange | 主章 L1，查询专题补部分 L2 | 把真实计划编号与参数生成、实例映射、接收端对象连起来 |
| 8 Pipeline | 局部 L2 | 补 task/queue/dependency 字段和事件时序，不只写 RUNNABLE 箭头 |
| 9 算子 | COUNT/AVG 局部 L2，Join/RF/Sort 多为 L1 | 先精读一个分组聚合，再分开分析 Join 与过滤传播 |
| 10—12 布局、读取、索引 | L1 为主，读取方法局部 L2 | 用一批行的候选 bitmap、行号、页和输出 Block 展开 |
| 13 更新与演进 | 状态机局部 L2，MOW 算法仍浅 | 给 Rowset/Segment/rowid 与位图的前后值、并发边界 |
| 14—16 导入与事务 | 局部 L2，16 章和专题 4 相对较强 | 把一次写入身份、提交信息、锁与可见版本的变化完整展开 |
| 17 版本读取 | 版本图示例有用，局部 L2 | 补对象持有和 stale/unused 清理条件及并发顺序 |

| 20—21 权限、治理 | 正常授权与队列有局部 L2；BE 内存较浅 | 选一个正常权限案例和一个资源等待案例，各自追到字段与回调 |
| 22—24 外部访问与扩展 | 字段映射/UDF 有局部 L2 | 一种 Connector 贯穿 FE range 到 BE Reader；不要并列罗列多个系统 |
| 25—26 Cloud | L1＋局部 L2 | 固定一种元数据模式，展开 key/value、冲突、提交和清理动作 |
| 27—28 贡献路径 | 27 章与历史案例是较好的 L2 范例 | 把历史补丁关键原码、恢复测试与断言放入正文，形成 L3 个案 |

**没有足够证据把整个核心章标为 L3/L4。** 历史查询实测是有用产物，但没有实现级跟踪和当前版本复现，不自动提升全章层级。

## 4. 最值得先补的六个实现案例

以下是书籍修订顺序，不是新增六项必交学习任务。

| 顺序 | 落点与固定案例 | 必须写出的内容 | 完成时读者能回答 |
|---|---|---|---|
| 1 | 第 5 章：Filter 穿过 Project | 规则匹配、Slot/ExprId、alias map、谓词拆分、重建树、一个拒绝案例、现有测试断言 | 哪个条件移动，为什么另一个留下，返回 null 表示什么？ |
| 2 | 第 16 章：普通内表提交到可见 | 一个 txn、两个分区的提交信息；next/visible version；表锁/事务锁；日志等待；发布检查 | 写入成功但未可见时，具体哪个条件未满足？ |
| 3 | 第 9 章：分组 COUNT/AVG | Block 列结构、分组键到 state 的映射、state 地址、add/merge/serialize、输出 | 每组的中间状态在哪里，跨片段传递什么？ |
| 4 | 第 8 章：任务等待和取消 | task/queue/dependency 的持有关系；block、唤醒、重入队、EOS/close；线程时序 | 等待时线程在做什么，取消如何让任务退出？ |

顺序考虑了读者的 Java 背景：先用一个可控规则建立精读标准，再深入最接近 FE 贡献方向的事务模块；之后沿执行、读取补 C++。这不是认定优化器比事务不重要，而是避免先陷入最大搜索框架。

第 18 章的持久化/恢复与历史 INSERT 统计修复可作为第二条 FE 贡献主线，穿插在第 2 个案例后阅读。IVM、Variant、Cloud 全部变体先不扩篇幅，待核心样章达标再精读。

## 5. 一个对照：第 5 章应该比现在多讲什么

原文已说“拆分可下推与保留谓词，经别名替换后重建计划”。接下来应展示真正决定行为的代码。

2026-10-14 只读核对本地 `fe/fe-core/src/main/java/org/apache/doris/nereids/rules/rewrite/PushDownFilterThroughProject.java` 的 `splitConjunctsByChildOutput()`，以下为关键条件原文，省略了方法外围：

```java
if (childOutputs.containsAll(conjunctSlots)
        && conjunctSlots.stream().map(childAlias::get).filter(Objects::nonNull)
                .noneMatch(Expression::containsVolatileOrNoneMovableExpression)) {
    pushDownPredicates.add(conjunct);
} else {
    remainPredicates.add(conjunct);
}
```

关键不是把条件翻译成中文，而是带具体对象走一遍。设 Project 输出 `revenue#20`，对应 producer 为 `amount#7`；Filter 的谓词是 `revenue#20 > 100`：

| 检查/动作 | 本例中的值或结果 |
|---|---|
| conjunctSlots | `{revenue#20}` |
| childOutputs | Project 输出集合，包含 revenue#20；这里不是直接取基表原列集合 |
| 第一个条件 | 为真，谓词不引用该 Project 输出范围之外的 Slot |
| alias map 查询 | revenue#20 → amount#7 |
| producer 是否含不可移动表达式 | 本例不含，通过 |
| 暂存集合 | 先把原谓词放入 pushDownPredicates |
| 后续 replace | 才把 revenue#20 替换为 amount#7 |
| 重建树 | Project 上保留输出身份，其 child 增加 Filter(amount#7 > 100) |

上述编号为教学身份，不是实际 EXPLAIN 输出。源码还包含压缩物化相关分支；样章主线可固定为不进入该分支，另设短节解释差异。

第二个例子把 producer 换成含随机表达式的计算，第二条件失败，谓词留在上面，避免筛选和输出重复求值。第三个例子引用外层 Slot，第一个条件失败。若所有谓词都留在上面，调用方返回 null 表示这条规则没有生成替代计划；若只有一部分保留，`PlanUtils.filterOrSelf()` 负责按需保留外层 Filter。

还应画出 Filter(Limit(Project)) 专门分支改写前后的树，明确 LIMIT 与 Filter 的相对顺序，而不是只写“注意 LIMIT”。最后将例子对应到已读测试的输入构造与断言。这样读者才能从规则思想走到实施条件。这段示范尚未替代完整样章，也未执行测试。

## 6. 每个核心案例的交付标准

1. **固定场景。** 一个 SQL/请求、最小表和数据，明确模型/模式/版本及关键配置。
2. **真正连通的调用图。** 区分直接调用、异步提交、RPC、回调；不能把职责图冒充调用栈。
3. **关键对象表。** 对象由谁创建、字段代表什么、谁修改、何时释放；数值例子沿全文保持身份一致。
4. **短源码摘录与推演。** 按职责分块，给文件和方法；代码来自具体快照，简化片段必须标明省略项。逐个重要分支解释条件、动作和理由。
5. **正确性及失败事件。** 至少一条拒绝、失败或并发案例；涉及锁的章节给持锁范围和可观察顺序。
6. **测试证据。** 选定真实 test 方法，写清 fixture、输入、调用和断言；运行结果另列，未执行就保留未执行。
7. **可继续维护的来源。** 精确仓库路径、方法与版本；重要摘录可以加文件摘要以识别漂移。文件存在检查只证明导航有效。

完整抄一千行源码不会自动达标；用少量关键片段解释清楚对象如何变化更有效。环境实验缺失也不妨碍把前六项中的静态分析写扎实。
