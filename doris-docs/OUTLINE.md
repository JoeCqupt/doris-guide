## 一、这本书要解决什么问题

面向有 Java 业务开发经验、刚接触数据库内核的开发者，建立一幅能够回到代码验证的 Doris 系统地图。读者应能说明一个用户行为经过哪些模块、数据和状态如何变化、失败会留下什么现象，以及应该在哪里修改和测试。

全书以订单分析场景贯穿：建表 → 写入 → 查询 → 更新 → 接入外部数据 → 排查性能与故障。先给出可观察的行为，再引出实现；C++、列存、分布式执行等知识在需要时补充。源码分析不等于把调用栈翻译成中文，每章围绕设计问题、关键对象、状态变化及边界条件展开。

成为持续贡献者是本书的实践方向。无需先读完整本书才能贡献；读者可以从 FE Java 的一个明确行为及其测试切入。Committer 邀请取决于长期贡献和社区认可，不作为读完本书的承诺。

### 为什么采用这样的分篇

- **OLAP 是工作负载与设计目标，MPP 是实现分布式分析的架构方式**：先讲二者关系，再分别展开优化、执行、存储、写入。
- **认证、授权、元数据和资源治理是系统基础能力**：不能因为不直接计算 SQL 就统称为“额外能力”。Web 控制台作为管理入口，与 HTTP API、可观测性一起讲。
- **Catalog 与 Connector 分层讲、放在同一篇**：从元数据抽象和管理生命周期走到实际数据访问，避免“外部 Catalog”和“外部集成”两处重复。
- **区分集成方向**：Doris 读取外部数据、外部系统向 Doris 写数据、客户端消费 Doris 查询结果，是三条不同链路。
- **存算分离独立成篇**：通过与存算一体对照，解释元数据、事务、缓存与故障边界的变化。

## 五、正文的统一写法与完成标准

每章采用下列骨架，具体小节可合并：

1. **问题与现象**：一个 SQL、操作或故障现象；本章范围、前置章节及部署模式。
2. **系统位置与设计**：组件关系图或时序图，说明为什么需要这些对象。
3. **源码精读**：3—6 个关键入口，记录路径、类/方法、核心字段、状态转换与调用证据。
4. **正常链路和边界**：成功条件、错误如何传播、并发/重试/恢复中的关键约束。
5. **验证与贡献连接**：已有测试位置、可复现实验及观察结果；哪些问题适合进一步调查。
6. **证据与延伸阅读**：commit、官方资料版本、已验证结论、推断及未核实事项。

章节完成须满足：主线能闭环、引用路径有效、关键结论有证据、示例标明执行状态、没有把计划实验写成实测结果。只读源码与运行验证分别标注。长代码只截取必要片段，避免大段复制和脱离上下文的逐行解释。

这是一份可持续维护的源码书，学习任务仍由 `doris-guide/stepN` 管理。书中实验可供选择，不自动变成必须完成的作业；个人构建问题放入实验记录，仅在确认具有普遍性后纳入正文。
