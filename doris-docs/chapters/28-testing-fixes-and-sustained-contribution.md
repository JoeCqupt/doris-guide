## 一、源码讲解：先找到决定行为的对象和分支

用最小的既有测试作落点：ShowLoadCommandTest.testApplyLimit 构造两行，limit=1/offset=1，断言返回第二行。它证明的是工具函数契约；真实 SQL 和重启证据证明的是其他层级。

### 先读这段真实代码

文件：`fe/fe-core/src/test/java/org/apache/doris/nereids/trees/plans/commands/ShowLoadCommandTest.java`，当前文件第 132—151 行。下面是连续原文摘录，局部片段省略了方法的其他部分；不要把片段当完整实现。

```java
    public void testApplyLimit() {
        UnboundSlot key = new UnboundSlot(Lists.newArrayList("LABEL"));
        List<OrderKey> orderKeys = Lists.newArrayList(new OrderKey(key, true, true));
        long limit = 1;
        long offset = 1;
        ShowLoadCommand sl = new ShowLoadCommand(null, orderKeys, limit, offset, "test");
        List<List<String>> rows = new ArrayList<>();
        List<String> row1 = new ArrayList<>();
        List<String> row2 = new ArrayList<>();
        row1.add("a");
        row1.add("b");
        row2.add("x");
        row2.add("y");
        rows.add(row1);
        rows.add(row2);
        rows = sl.applyLimit(limit, offset, rows);
        Assertions.assertEquals(1, rows.size());
        Assertions.assertEquals("x", rows.get(0).get(0));
        Assertions.assertEquals("y", rows.get(0).get(1));
    }
```

### 这几行应该怎样读

测试先构造 [a,b]、[x,y] 两行，再按 offset=1/limit=1 截取。三条断言分别检查行数和两个单元格，证明内容而不仅是长度；它并没有经过 SQL 解析和真实 LoadManager。

### 从“看懂了”到“别人能够验证”

第 27 章给出了 SHOW LOAD 的定位案例。真正形成贡献还要回答：这个行为是否需要改变，最小修改是什么，怎样证明修好了并且没有破坏相关行为？

代码、测试、说明和后续维护共同组成一个成果。构建成功是环境与编译层面的证据，不等于发现了产品缺陷；一个 PR 被接受也不等于整个模块已经掌握。长期目标应落实到持续解决有价值的问题，而不以提交数量或承诺的日期判断 Committer 资格。

本章不挑选当前开放 issue，也没有代用户对外发消息或提交代码。涉及具体社区题目时，必须重新核对认领、已有修复和相关讨论。

### 先写清行为约定

一个待修复问题至少需要：最小输入、实际结果、合理预期、发生条件和版本。预期应来自文档、已有契约或一致的语义，而不是“我觉得这样更好”。

例如对 SHOW LOAD 的排序问题，应区分条件筛选、列下标映射、比较规则、分页和显示。只说“返回不对”无法决定改哪个模块。若实际只是使用了不同版本或错误参数，解释清楚用法同样有价值，但不应制造一个代码修复。

本地构建问题先查官方说明、工具链、依赖版本与实际命令。只有确认标准支持路径在明确条件下失败，并且根因属于项目代码，才进入修复论证。

## 四、回到源码解释：把现象还原成执行过程

有效测试针对用户契约，而不是复刻实现细节。单测、SQL、重启三层证据各自有适用范围；写清边界比笼统“全部通过”更能建立维护者信任。持续贡献从这种可核验判断开始。

### 用自己的话走完这条链

合上结果后，按“输入 → 关键对象/状态 → 分支条件 → 可观察结果”的顺序回答本章问题：**怎样把“我看懂了”变成维护者能核验的贡献？** 再指出一项尚不能从现有实验得出的结论。能把每个箭头落到本章的方法或证据，比记住术语更接近读懂源码。

### 选择能区分对错的最小测试

| 验证层级 | 能证明什么 | 典型不足 |
|---|---|---|
| FE 单测 | 表达式、命令、元数据或状态逻辑 | 不一定覆盖真实协议和 BE |
| BE 单测 | 数据结构、算子、存储和生命周期局部行为 | 不一定覆盖 FE 规划和跨节点协作 |
| SQL 回归 | 用户可见结果与异常 | 结果正确不一定证明并发/性能性质 |
| 集成或故障实验 | 真实服务、恢复、分布式事件关系 | 成本高，必须控制环境与干扰 |

有效测试应在原问题条件下失败，并在修复后满足预期。若只是按照新实现的分支逐句造输入，它可能只是在重复实现而没有验证用户约定。

对不可稳定复现的并发问题，应先明确事件顺序和状态约束，再选可控调度或故障注入方式；反复运行直到偶然通过，不能当作修复证据。

本书遵循本任务的仓库要求：构建使用 `build.sh`，非性能测试保持 ASAN；测试使用预设脚本。下面是可选命令说明，**本次没有执行**。

是否执行了预期测试，要检查报告中的数量、失败/跳过情况和退出码。测试通过也不自动意味着所有 Checkstyle、格式或静态分析都完成；按改动类型补齐仓库要求，并诚实记录未执行项。

### 回归结果不能手工写成“通过”

新增 SQL 回归应保持确定性，例如必要时 ORDER BY 或使用 `order_qt`。预期错误使用项目约定的 `test { sql ...; exception ... }` 形式。结果文件通过脚本生成并检查，不能把自己希望看到的输出手写进文件，伪装成实际运行结果。

测试数据生命周期也遵循仓库规则：建表前清理同名测试表，测试结束保留现场便于调试。不要让普通测试依赖用户业务表或本书示例表已有的数据。

配置只设置验证该行为必需的项，避免一份测试悄悄依赖大量临时开关。环境、端口和调试文件与实际产品改动分开，不能一起加入代码提交。

### 小改动也要看关联边界

修改共用分页工具，要检查其他调用方；修改聚合状态，要考虑序列化与合并；修改元数据字段，要考虑恢复和旧格式；修改队列逻辑，要检查取消和资源释放。

这些检查由问题本身决定，不需要每次扩成全库重构。理想的修改范围足够小，又完整覆盖根因。若必须调整多个模块，应在说明中把触发条件和模块关系串起来。

写代码前参考现有类似实现，写完按仓库的 review、风格、测试要求完成自查。本章只介绍工作方法，并未对某个补丁开展代码审查。

### 一份便于 review 的说明

先描述用户能遇到的问题，再描述改变后的行为与验证。例如可以采用下面的结构，而不是只列“修改 A、修改 B”：

```text
触发条件：在什么版本、配置和输入下发生。
原有行为：具体结果或错误。
原因：哪段代码的哪个前提不成立。
修改：如何恢复正确约定，影响哪些调用方。
验证：真实执行了哪些测试，结果怎样，哪些仍未验证。
```

提交格式按仓库模板填写 `[type](module)` 标题、Problem Summary、Release note 与检查项。有真实对应 issue 时再填写关联，不能编造编号。对用户可见行为改变要明确说明，纯重构也要解释为何需要。

响应 review 时，先确认对方关注的是语义、兼容性、测试还是维护成本。不同意时用具体案例或代码证据解释；接受修改时更新测试与说明，避免文档仍描述旧方案。

### 把知识沉淀到一个稳定方向

以你的 Java 背景，可以围绕 FE 命令、导入任务、事务观察或元数据持续积累：第一次解释一个行为，下一次补齐能区分边界的验证，再处理确认的问题，并跟进合入后的反馈。

贡献不只有代码。清楚的复现、有效的测试、准确的文档勘误、认真回复使用问题，都可能降低维护者的工作成本。是否值得贡献取决于实际价值，不取决于成果形式。

维护一份简短记录即可：问题、证据、社区反馈、最终结果和下一次仍需补足的知识。个人环境修复可以记录为学习成果，但不要自动算成项目贡献。
