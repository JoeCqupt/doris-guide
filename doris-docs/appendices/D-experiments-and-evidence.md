## D.2 先确认实际运行的版本

源码 HEAD、构建产物、正在运行的服务是三个对象。读过最新源码但连接旧服务时，SQL 或 Profile 差异可能来自版本而非代码缺陷。先记录源码 commit 与修改状态，再记录服务报告的版本、启动目录和使用的配置。

最小环境记录应包括操作系统与架构、部署形态、FE/BE 数量、客户端、相关配置和 Session 参数。外部表补充 Connector 与外部系统版本、表快照；性能实验补充数据规模、并发、缓存条件和重复次数。

## D.3 实验记录模板

下面的空模板用于今后实验，不是已运行结果：

```text
实验问题：
日期与操作者：
源码 commit / 本地差异：
实际服务版本 / 部署形态：
数据与前置条件：
执行的完整命令或 SQL：
预期及其依据：
实际结果文件 / Query ID / 日志时间段：
相关 EXPLAIN / Profile：
是否符合预期：
异常、剩余疑问与清理说明：
```

失败也是有效结果，应保留退出码和原始日志，不把修正后的推测写成原始输出。日志中的凭据等信息应在分享前移除，保持必要的错误上下文与身份关联。

## D.4 推荐的逐步验证顺序

先运行八行订单闭环，确认版本和结果；再选一条聚合查询保存 EXPLAIN 与 Profile；最后根据关注方向选择外表或 Cloud 环境。无需为读完本书同时搭建所有系统。

实验前阅读脚本内容并选择自己的测试数据库。回归结果文件由项目脚本生成，不能把书中的预期值手填为回归结果。启动服务、执行 SQL 和测试需要额外时间，本次章节补齐没有进行这些操作。

本书未新增未执行的 Shell 一键部署方案，也未提供虚构的性能对比数字。具体构建与测试约定见[第 28 章](../chapters/28-testing-fixes-and-sustained-contribution.md)。
